# Design document: Motion Logger

> **Чернетка (29.10.2026).** Розділ «Результати» заповнюється після запуску на платі. Фінальна версія має вміщатись у 2–4 сторінки PDF.

## 1. Задача

Пристрій на Raspberry Pi 5 збирає дані двох акселерометрів (MPU6050 по I2C, ADXL345 по SPI) і GPS-модуля (NEO-6M по UART), визначає, чи плата рухається, і пише журнал у файл. Система збирається у власний образ Buildroot, що завантажується з microSD і сам запускає програму `motion_logger`. Складність задачі свідомо в системному шарі (Device Tree, драйвери ядра, потоки, `epoll`, образ), а не в самих датчиках.

## 2. Загальна схема

    MPU6050 (I2C1) ──► драйвер ядра ──► /sys/bus/iio/…/in_accel_*_raw ──► потік «основний акселерометр» ─┐
    ADXL345 (SPI0) ──► драйвер ядра ──► /sys/bus/iio/…/in_accel_*_raw ──► потік «додатковий акселерометр» ─┼─► кільцевий буфер
    NEO-6M  (UART2) ──► /dev/ttyAMA2 ──► epoll ──► розбір NMEA ──────────► потік «GPS» ────────────────────┘     (mutex)
                                                                                                                  │
                                                                         потік-записувач ◄───────────────────────┘
                                                                         фільтр руху → рядки JSON у лог-файл

Код розділено на три шари: `interfaces/` (що вміє датчик: «дай відлік»), `drivers/` (як читати конкретне джерело: IIO, послідовний порт, файл CSV) і `core/` (буфер, фільтр, лог, розбір NMEA). `core/` не підключає нічого з `drivers/`; зв'язує їх лише `main.c`. Тому замість справжнього датчика можна підставити програвач CSV-запису, і вся логіка перевіряється без плати.

## 3. Прийняті рішення і чому

| Рішення | Чому |
|---|---|
| Linux на SBC, а не мікроконтролер | проєкт перевіряє роботу з повним стеком (DTS, IIO, `epoll`, `pthread`, образ), яку на мікроконтролері не показати |
| Датчики через драйвери ядра (IIO), а не `i2c-dev`/`spidev` | драйвер ядра відповідає за регістри і масштаб; програма читає звичайні файли. Юрій (ментор) підтвердив підхід, головна умова: датчик має давати потрібну частоту (100 Гц) |
| Опис заліза власним overlay, не правкою базового дерева | змінюємо тільки своє (I2C1 + MPU6050, SPI0 + ADXL345), база лишається від виробника; датчики описуються на рівні Linux DTS, не в U-Boot (порада ментора) |
| Один потік на джерело + один потік-записувач, спільний кільцевий буфер із mutex | повільний запис у файл не гальмує опитування датчиків; нічого не губиться, поки буфер не повний (втрати рахуються й видно в підсумку) |
| `epoll` для GPS, `clock_nanosleep` з абсолютними моментами для IIO | потік спить, поки нема даних; період 10 мс не «пливе», бо кожен крок рахується від попереднього, а не від «зараз» |
| Рух: відхилення довжини вектора прискорення від його повільного середнього + ковзне середнє + поріг | не залежить від орієнтації плати і від похибки масштабу датчика (нерухомий MPU6050 показує 0,942 g, не 1 g); параметри (вікно 50, поріг 0,02 g, підтвердження 50 відліків) підібрано за записом 01.11.2026 |
| В лог не кожен відлік, а події руху + підсумок кожної секунди | 100 рядків на секунду це години логу, з якого людині довелося б вручну шукати «коли я йшов» |
| Формат логу JSON Lines | один рядок = один запис; читає і людина, і програма; рядок пишеться одним `write()` у файл з `O_APPEND`, тож не буває напівзаписаного рядка |
| Автозапуск скриптом BusyBox init (`S99motion_logger`) | у Buildroot це стандартний init; скрипт ідемпотентний, `stop` чекає SIGTERM і добиває SIGKILL, параметри в `/etc/default/motion_logger` |
| Координати GPS лише за статусом `A` в `RMC` | модуль без фіксації може повторювати останню позицію або видавати порожні поля; нульова широта не повинна потрапити в лог як точка на екваторі |

## 4. Образ і збірка

Buildroot 2026.08 з зовнішнім деревом `BR2_EXTERNAL` (`MOTION_LOGGER`): `configs/motion_logger_defconfig`, пакет `package/motion_logger` (збирає `app/` тим самим крос-тулчейном, що й образ), `board/motion_logger/` (`config.txt`, `cmdline.txt`, overlay датчиків, фрагмент ядра для ADXL345, rootfs overlay із `S99motion_logger` та `modules-load.d`). Драйвери ядра зібрано модулями, тому їх підвантажує `S11modules`. Консоль відлагодження на UART `DBG1` (GPIO14/15); у серійному виробі такі виводи прибирають, бо вони відкривають будову прошивки. Опис overlay: `docs/dts-overlay.md`.

## 5. Як перевірялось

- Модульні тести на кожен шар без плати: буфер, розбір NMEA, фільтр руху, події, драйвер IIO на «підробному» каталозі `/sys`, читач GPS на каналі (`make test`), під ThreadSanitizer (`make test-tsan`) та ASan/UBSan; крос-збірка aarch64 статично.
- Наскрізні перевірки: `make check-samples` (звіт по CSV збігається з еталоном), `make check-replay` (події в лозі збігаються з `analyze_recording`), `make check-sources` (три джерела в одному лозі, `SIGTERM`).
- Навмисні поломки коду («мутації»): тест має почервоніти; для нових модулів усі 8 перевірених мутацій спіймано.
- Скрипт автозапуску перевіряється `board/motion_logger/tests/check_init_script.sh` (чекліст Ajax з презентації про init).
- Плата Motion Logger v2 прийнята після спаювання (25.10.2026): усі три датчики працювали на Raspberry Pi OS; GPS всередині будинку дає хибну позицію (спуфінг), тому справжній запис робиться надворі.

## 6. Що не вийшло або ще не перевірено

- Власний образ із датчиками ще не завантажувався на платі: корпус друкується, консольний кабель JST-SH очікується.
- Поріг руху і вікно фільтра підібрані за одним записом (60 с спокою, 60 с ходьби, одна людина); для інших умов не перевірялись.
- Невідомо, з якою частотою реально віддають відліки датчики через IIO (треба перевірити `sampling_frequency`, MPU6050 за замовчуванням може бути 50 Гц).
- U-Boot між прошивкою Pi 5 і ядром (крок 4.7) ще не запускався.

## 7. Результати (заповнити після запуску на платі)

- Запис «лежить / ходьба»: графік відхилення, моменти `MOVE_START` і `MOVE_STOP`, порівняння з ручною розміткою.
- Фактична частота відліків IIO.
- Розмір образу, час завантаження до запуску програми, розмір логу за годину.
